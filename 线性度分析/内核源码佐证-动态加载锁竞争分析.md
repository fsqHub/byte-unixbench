## 二、数据结构层——锁字段定位

### 2.1 `struct address_space`（每个文件的 Page Cache 根对象）

**源码路径**：`include/linux/fs.h` L474–L524

```c
/**
 * struct address_space - Contents of a cacheable, mappable object.
 * @i_mmap:      Tree of private and shared mappings.
 * @i_mmap_rwsem: Protects @i_mmap and @i_mmap_writable.   ← 原文重点
 * ...
 */
struct address_space {
    struct inode        *host;
    struct xarray        i_pages;        // Page Cache，内部有 xa_lock
    struct rw_semaphore  invalidate_lock;
    atomic_t             i_mmap_writable;
    struct rb_root_cached i_mmap;        // 文件的 VMA 区间树
    ...
    struct rw_semaphore  i_mmap_rwsem;   // L514：保护 i_mmap 区间树
    ...
};
```

**结论**：原文档"文件映射树读写信号量 (`i_mmap_rwsem`)"的定性**完全正确**。
该锁定义在 `address_space`（每文件一个），而非 `inode` 本身，因此它是**文件级全局竞争点**：40 个容器共用同一份 `.so` 文件时，对应同一个 `address_space` 对象，同一把 `i_mmap_rwsem`。

### 2.2 `struct inode`（文件元数据对象）

**源码路径**：`include/linux/fs.h` L673–L788

```c
struct inode {
    ...
    atomic_t    i_count;      // L747：引用计数，原子操作
    ...
    struct rw_semaphore i_rwsem;  // L723：inode 级互斥锁
    ...
    struct address_space i_data;  // L758：内嵌的 address_space
};
```

**结论**：原文"原子引用计数 (`i_count`)"**正确**。每次 `open()`/`close()` 均触发 `atomic_inc`/`atomic_dec`，在 320 核下引发 Cache Line Bouncing。

### 2.3 `struct mm_struct`（进程地址空间）

**源码路径**：`include/linux/mm_types.h` L755–L848

```c
struct mm_struct {
    struct {
        ...
        spinlock_t  page_table_lock;  // L833：页表自旋锁
        struct rw_semaphore mmap_lock; // L848：进程 VMA 链表锁
        ...
    };
};
```

**结论**：原文"进程地址空间锁 (`mmap_lock`)"**正确**，且源码注释特别指出其两个热字段布局经过专门的缓存行优化（L836–L847 注释），说明该锁本身已是高竞争已知问题。

## 三、锁的调用链——加锁路径核查

### 3.1 内核官方锁顺序文档

**最具权威性的一手证据**在 `mm/filemap.c` L82–L129，这是 Linux 内核中少有的**官方全局锁顺序注释**：

```
// mm/filemap.c L82–L129
/*
 * Lock ordering:
 *
 *  ->i_mmap_rwsem         (truncate_pagecache)
 *    ->private_lock       (__free_pte->block_dirty_folio)
 *      ->swap_lock
 *        ->i_pages lock   ← xa_lock（XArray 自旋锁）
 *
 *  ->i_rwsem
 *    ->invalidate_lock
 *      ->i_mmap_rwsem     (truncate->unmap_mapping_range)
 *
 *  ->mmap_lock
 *    ->i_mmap_rwsem
 *      ->page_table_lock or pte_lock
 *        ->i_pages lock   (arch-dependent flush_dcache_mmap_lock)
 *
 *  ->mmap_lock
 *    ->invalidate_lock    (filemap_fault)
 *      ->lock_page        (filemap_fault, access_process_vm)
 * ...
 */
```

这段注释**直接证实**了原文档描述的全部锁依赖链：
- `mmap_lock → i_mmap_rwsem → page_table_lock → i_pages lock`
- `mmap_lock → invalidate_lock → lock_page（folio_lock）`

### 3.2 阶段一 `openat`：引用计数原子操作

原文主张：打开文件时 `dentry` 和 `inode` 的 `i_count` 原子递增。

**源码证据**：`include/linux/fs.h` L747
```c
atomic_t    i_count;   // inode 引用计数，atomic_inc/dec 操作
```

`dentry` 的引用计数同理由 `d_lockref`（基于 `spinlock` + `refcount`）保护。在 320 核同时 `openat` 同一 `.so` 时，`atomic_inc(&inode->i_count)` 指令触发 ARM64 的 `LDADD`（LSE）或 `LDXR/STXR`（LL/SC）独占访存序列，跨 NUMA 节点时延高达数百纳秒每次。

**结论**：原文描述**正确**。

---

### 3.3 阶段二 `mmap`：`i_mmap_rwsem` 写锁——最重要的竞争点

原文主张：`mmap` 时须获取 `i_mmap_rwsem` 写锁，将新 VMA 插入文件的区间树。

**源码证据 A**：`mm/mmap.c` L440–L451，`vma_link_file()` 函数

```c
// mm/mmap.c L440–L451
static void vma_link_file(struct vm_area_struct *vma)
{
    struct file *file = vma->vm_file;
    struct address_space *mapping;

    if (file) {
        mapping = file->f_mapping;
        i_mmap_lock_write(mapping);    // ← 加写锁
        __vma_link_file(vma, mapping); // ← 插入 i_mmap 区间树
        i_mmap_unlock_write(mapping);  // ← 释放写锁
    }
}
```

**源码证据 B**：`include/linux/fs.h` L544–L546，`i_mmap_lock_write()` 实现

```c
// include/linux/fs.h L544–L546
static inline void i_mmap_lock_write(struct address_space *mapping)
{
    down_write(&mapping->i_mmap_rwsem);  // ← 睡眠级写锁
}
```

**关键说明**：`down_write()` 是**睡眠锁**（非自旋锁），在高竞争下会触发内核调度，导致 CPU 上下文切换。320 核争抢同一把锁时，等待队列会不断膨胀，每次 `exec` 都要排队等待其他 319 个核完成 VMA 插入操作。

**结论**：原文描述**完全正确且精确**，`i_mmap_rwsem` 确是"极重度灾区"。

### 3.5 阶段三 缺页中断：`xa_lock` 与 `folio_lock`

原文主张：缺页中断时触发 Page Cache XArray 的自旋锁 (`xa_lock`)，以及页锁 (`PG_locked`/`folio_lock`)。

**源码证据 A**：Page Cache 使用 XArray 存储，其内部锁为 `xa_lock`（`xarray.h`），`filemap_remove_folio()` 中可直接观察到：

```c
// mm/filemap.c L253–L264
void filemap_remove_folio(struct folio *folio)
{
    struct address_space *mapping = folio->mapping;
    BUG_ON(!folio_test_locked(folio));
    spin_lock(&mapping->host->i_lock);
    xa_lock_irq(&mapping->i_pages);   // ← XArray 自旋锁
    __filemap_remove_folio(folio, NULL);
    xa_unlock_irq(&mapping->i_pages); // ← 释放
    ...
}
```

**源码证据 B**：缺页中断路径中的 `folio_trylock()` / `__folio_lock()`（即 `PG_locked` 位锁），在 `mm/filemap.c` L3129–L3161 的 `lock_folio_maybe_drop_mmap()` 中：

```c
// mm/filemap.c L3129–L3161
static int lock_folio_maybe_drop_mmap(struct vm_fault *vmf, struct folio *folio,
                                      struct file **fpin)
{
    if (folio_trylock(folio))   // ← 尝试获取页锁（PG_locked 位）
        return 1;
    ...
    __folio_lock(folio);        // ← 睡眠等待页锁释放
    return 1;
}
```

**结论**：原文描述**正确**。第一个读入某页的核持有 `PG_locked`，其余 319 个核若触发同一页的缺页中断，将在 `folio_wait_locked()` 中睡眠。

**须补充的细节**：原文将 `xa_lock` 称为"Page Cache 自旋锁"，更精确的描述是：  
- `xa_lock` 是 `struct xarray`（即 `address_space.i_pages`）内部的 `spinlock_t`  
- 它在查找/插入 Page Cache 条目时以 `xas_lock()`/`xa_lock_irq()` 的形式被持有  
- 由于是**禁中断自旋锁**，竞争时不会睡眠，而是空转消耗 CPU 周期

### 3.6 阶段四 `mprotect` 与 TLB Shootdown

原文主张：`mprotect` 修改页表后必须向所有核发送 IPI 刷新 TLB。

**源码证据**：`mm/mmap.c` L93–L105，`vma_set_page_prot()` 函数：

```c
// mm/mmap.c L93–L106
void vma_set_page_prot(struct vm_area_struct *vma)
{
    unsigned long vm_flags = vma->vm_flags;
    pgprot_t vm_page_prot;

    vm_page_prot = vm_pgprot_modify(vma->vm_page_prot, vm_flags);
    ...
    /* remove_protection_ptes reads vma->vm_page_prot without mmap_lock */
    WRITE_ONCE(vma->vm_page_prot, vm_page_prot);
}
```

`mprotect` 系统调用最终经 `change_prot_pte()` → `flush_tlb_range()` → 平台 IPI 路径完成 TLB 刷新。在 ARM64 上对应 `arch/arm64/mm/tlb.c` 中的 `__flush_tlb_range()`，通过 `dsb(ishst)` + `tlbi` 指令序列实现跨核 TLB 失效，涉及 Inner Shareable 域的广播。

**结论**：原文描述**正确**，在 320 核 NUMA 系统中该 IPI 广播代价极高。

### 3.7 阶段五 进程退出：`i_mmap_rwsem` 再次争锁

原文主张：进程退出时必须再次加写锁，将 VMA 从文件的区间树摘除。

**源码证据**：`mm/mmap.c` L126–L136，`unlink_file_vma()` 函数

```c
// mm/mmap.c L126–L136
void unlink_file_vma(struct vm_area_struct *vma)
{
    struct file *file = vma->vm_file;

    if (file) {
        struct address_space *mapping = file->f_mapping;
        i_mmap_lock_write(mapping);          // ← 加写锁
        __remove_shared_vm_struct(vma, mapping); // ← 从区间树摘除
        i_mmap_unlock_write(mapping);        // ← 释放写锁
    }
}
```

同时 `__remove_shared_vm_struct()`（L111–L120）中调用 `mapping_unmap_writable()`，该函数内部是 `atomic_dec(&mapping->i_mmap_writable)`——原子操作再次上场。

**结论**：原文描述**完全正确**，每次 exec 结束后退出，第二次排队 `i_mmap_rwsem` 写锁不可避免。

**唯一须精化的表述**：原文将 `xa_lock` 描述为"Page Cache 树的读写自旋锁"，实际上 XArray 在读路径使用 RCU（无锁读），只在**写路径**（插入/删除 Page Cache 条目）才持有 `xa_lock`。缺页中断从 Page Cache **读**已有页时走 RCU 快路径，无锁；只有**第一次**将物理页插入 Page Cache 时才触发 `xa_lock` 竞争。原文整体逻辑无误，但该细节值得注意。

## 五、完整锁依赖链（源码级还原）

以下是一次 `exec` 动态链接程序完整生命周期内，操作**同一个 `.so` 文件 Inode** 所触发的锁序列：

```
exec() 触发 ld-linux 加载 libc.so
│
├─ [openat] ──────────────────────────── fs.h L747
│   └─ atomic_inc(&inode->i_count)        # Cache Line Bouncing
│
├─ [mmap 代码段] ──────────────────────── mmap.c L440–L451
│   ├─ mmap_write_lock(mm)                # mm_types.h L848（进程级，不跨进程）
│   ├─ i_mmap_lock_write(mapping)         # fs.h L546  ← 全局竞争点①
│   │   └─ vma_interval_tree_insert()     # 插入 i_mmap 区间树
│   └─ i_mmap_unlock_write(mapping)
│
├─ [首次缺页中断 Page Fault] ──────────── filemap.c L3132
│   ├─ RCU 快路径查 Page Cache（无锁）
│   ├─ [页不在 Cache] xa_lock_irq()       # filemap.c L259  ← 全局竞争点②
│   │   └─ 插入物理页到 i_pages XArray
│   ├─ folio_lock()                       # filemap.c L3158 ← 全局竞争点③

│

│   ├─ i_mmap_lock_write(mapping)         # 再次加写锁
│   ├─ 修改 PTE 权限

└─ [进程退出 munmap] ──────────────────── mmap.c L126–L136

    │   └─ vma_interval_tree_remove()     # 从区间树摘除
```

## 六、为什么独立挂载 so 文件能获得 8-9 倍提升——锁视角的量化分析

| 维度 | 共享 so（优化前） | 独立 so（优化后） |
|---|---|---|
| `i_mmap_rwsem` 竞争规模 | 320 核争 **1 把**睡眠写锁 | 8 核争 **各自 1 把**（共 40 把）|
| `i_count` 原子操作范围 | 320 核争 **1 个**缓存行 | 8 核争 **各自 1 个**缓存行 |
| XArray `xa_lock` 范围 | 320 核争 **1 棵** XArray | 8 核争 **各自 1 棵** |
| NUMA 跨节点访问 | 高频（跨 NUMA 域） | 低频（8 核通常在同一 NUMA 节点）|
| TLB Shootdown 代价 | 无变化（进程级操作） | 无变化（进程级操作）|

锁竞争强度从 **`O(N)` 争 1 把锁**降低到 **`O(N/K)` 争各自 1 把锁**（N=320, K=40），理论极限提升 K=40 倍，实测 8-9 倍符合预期（受到其他非锁瓶颈如缺页中断、TLB miss 的稀释）。
